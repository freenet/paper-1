\section{Implementation Status and Open Problems}
\label{sec:status}

This section describes the reference implementation, makes the implementation status of each major mechanism explicit, and lists the architectural questions we view as open.

\subsection{Implementation}

The Freenet Core is implemented in Rust as an asynchronous \texttt{tokio}-based runtime. Contracts and delegates execute inside Wasmtime \citep{wasmtime}; both run under per-instance fuel limits and explicit memory bounds so that a runaway or malicious module cannot exhaust the host. Contract state is persisted through a pluggable store layer with implementations on top of \texttt{redb} \citep{redb} and SQLite.

The runtime is organized as a single central event loop, a \texttt{tokio::select!} over inbound transport packets, client API events, operation timers, and background tasks, that dispatches into per-operation state machines. The single-coordinator design simplifies reasoning about partial state but limits the throughput of a single peer to what one event-loop thread can sustain. So far this has not been the binding constraint in deployment.

\paragraph{Deterministic simulation testing.} A peer-to-peer system is hard to test by ordinary means: many bugs in routing, congestion, or convergence appear only in specific multi-peer interleavings that are difficult to reproduce. The Core ships with a deterministic simulation harness built on Turmoil \citep{turmoil}: virtual time, a seeded global RNG, an in-memory socket implementation, and fault-injection knobs for loss, latency, partitions, and reorderings. Tests run the entire network in a single deterministic process and replay bit-for-bit from a seed. Most non-trivial routing, subscription, and contract-execution bugs we have found were first reproduced in simulation.

\paragraph{Content-addressed components.} Contracts, delegates, and UI bundles are all addressed by hash. This pushes a lot of complexity off the platform: there is no version negotiation, no upgrade protocol, no need for the platform to understand application semantics during deployment. A new version is published under a new key; the old key continues to work as long as anyone hosts it.

The single biggest gap between this paper's narrative and the deployed system is congestion control. The platform supports pluggable congestion controllers but the deployed default is a token-bucket fixed-rate scheme. LEDBAT++ and BBR variants exist in the codebase as alternatives, but neither has yet been adapted to the workload satisfactorily. Real congestion control across heterogeneous peer-to-peer links remains open work.

\subsection{Where the Platform Fits}

The combination of contract-defined merge, summary/delta sync, small-world routing, and delegates is well-matched to applications whose consistency requirements are conflict-mergeable in some application-defined sense. Group chat, collaborative documents, social feeds, reputation systems, asynchronous email-like inboxes, and identity directories are all in the well-fit class. A working chat implementation \citep{river} and an anonymous identity scheme \citep{ghostkey} are deployed against the live network.

\subsection{Where the Platform Does Not Fit}

Several application classes do not fit the model gracefully, and we want to be explicit about them.

\paragraph{Strictly linearizable transactions.} A defense against double-spending fungible tokens requires that two attempts to spend the same balance cannot both succeed. The merge model cannot express ``one of these updates is rejected unconditionally''; merge is total. Concretely, fungible-token transfer with platform-level double-spend protection cannot be expressed by a single contract in the current model. Applications that need a strong-consistency primitive must either contain the inconsistency inside a contract whose validity predicate detects and rejects the second update (which forces the conflict into application code, with the loser's state restored on detection) or layer an auxiliary consensus mechanism on top of the platform.

This limitation is not confined to currency, and it cuts into the well-fit list above. Reputation is a good example: a reputation system that only \emph{accumulates} endorsements is monotone and fits the merge model cleanly, but the moment it needs to \emph{revoke} a credential, \emph{slash} a stake, or otherwise spend down a balance, it inherits exactly the ``reject the second spend'' requirement that merge cannot express. Applications in the well-fit class thus have a foot in the poorly-fit class to the extent that their semantics are spend-shaped rather than accumulate-only.

\paragraph{Abuse-resistant open posting.} A purely-open contract is simple to write as a set under union and equally simple to flood. Practical contracts in this class restrict writes to signed records by approved keys, charge a proof-of-work fee per update, or require credentials issued by a reputation contract. The platform's transport-layer rate limiting and per-neighbor resource accounting do provide a partial floor: a neighbor consuming excessive resources is disconnected, which caps the volume any single attacker can push through any single peer. That bound is useful but limited; it does not stop a distributed flood from many cheap identities, nor a slow-burn pattern that stays within per-peer limits. The platform has no application-level spam defense beyond that transport floor.

\paragraph{Coordinated DoS.} Per-peer resource limits protect a peer against a single misbehaving neighbor, not against coordinated traffic from many neighbors using cheap identities. Defenses here probably require accounting that persists across identities, which is the open incentive layer noted above.

\paragraph{Durable storage of cold state.} Contract state persists only as long as some peer near $\ell(\contract)$ keeps it, and each peer holds contracts in a byte-budgeted cache --- an LRU with a demand-ordered eviction policy and a short protective TTL --- whose size the operator sets. Reads, updates, and active subscriptions keep a contract near the top of that cache; a contract that goes \emph{cold} (no reads, no subscribers, no recent updates) is an eviction candidate on every peer that holds it. Nothing in the platform re-replicates a contract to maintain a target replica count: when a hosting peer evicts, no other peer is recruited to take its place, and a loss or divergence is repaired only by a fresh \textsf{PUT} from someone who still holds the state. An unpopular contract's state can therefore be evicted from every peer that hosts it and become unrecoverable. The platform makes \emph{no durability guarantee} for cold state; persistence is emergent from access patterns and the replication factor, not a promise. This is the same property the original Freenet had, and it bears on precisely the long-lived applications this paper foregrounds --- a dormant collaborative document, an inbox nobody has polled, an identity-directory entry for an inactive user all hold state that may sit cold for long periods. A mechanism that maintains a minimum replica count independently of demand (active repair, incentivised pinning, or explicit archival contracts) is open work.

\subsection{Open Problems}

We treat the following as genuinely open and intend them as subjects of future work or empirical evaluation.

\begin{enumerate}[leftmargin=1.4em, itemsep=2pt]
  \item \textbf{Scaling characterization.} The single 24-hour data point in \cref{sec:routing-measurement} is consistent with logarithmic-diameter routing at the deployed network size. A real characterization requires scanning $N$ across orders of magnitude. We do not currently have the deployment to do this; controlled simulation studies are the interim alternative, though (\cref{sec:routing-measurement}) producing the curve requires extending the deterministic harness to emit hop-count-versus-$N$ data it does not produce today.
  \item \textbf{Failure modes of contract-defined merge.} A contract whose merge is not actually associative or idempotent does not converge; the platform's handling of this is currently to allow the divergence to be observable but not to take corrective action. Better diagnostics, and where feasible contract-level invariants checked at the platform layer, are open work. A concrete near-term step, short of platform-enforced checking, is to ship a property-based test harness as first-class contract tooling: QuickCheck-style generation of states and updates that exercises associativity, commutativity, and idempotence of $\merge_\contract$, and the sync-soundness property (\cref{prop:sync}), for a given contract. Such a harness does not bind a malicious author, who simply will not run it, but it converts the monoid-law and sync-soundness obligations from an honour system into a supported, CI-able workflow for honest authors.
  \item \textbf{Congestion control.} As above. The current fixed-rate default is a deliberate choice not to ship something we cannot tune correctly, not an endorsement of fixed-rate as the right answer.
  \item \textbf{Sybil-resistant identity.} The application-layer approach has examples (Ghost Keys) but no clean general story, and the gap is deeper than ``unfinished.'' Because identity and reputation contracts are themselves routed and replicated through the location layer they are meant to secure, the defense is circular: an adversary with enough address prefixes to crowd a contract's location can both serve poisoned reads of that contract and keep honest writes from reaching its canonical replicas (\cref{sec:trust}). The prefix hash's honest-collision behaviour compounds this by eroding the geographic diversity of honest peers the bootstrap would rely on. Breaking the circularity needs something the platform does not currently provide --- ring-distance separation guarantees among replicas of safety-critical contracts, demonstrable geographic diversity of honest peers near their locations, or out-of-band trust anchors for the handful of contracts that bootstrap the rest. This is the recurrent question for every decentralized platform, and we do not claim to have solved it.
  \item \textbf{Incentive / abuse layer.} How a network as a whole resists coordinated denial of service without a centralized authority, while still allowing low-friction joining, is the work that determines whether the network grows past a small community.
  \item \textbf{Durability of cold state.} As noted in \cref{sec:status} above, the platform makes no persistence guarantee for a contract that no one is reading, subscribing to, or updating: its state can be evicted from every hosting peer's cache and lost. A mechanism that maintains a minimum replica count independently of demand --- active repair, incentivised pinning, or explicit archival contracts --- without reintroducing an unbounded free-storage abuse surface is open work, and for the long-lived applications the platform targets it is arguably as load-bearing as the consistency story.
\end{enumerate}
