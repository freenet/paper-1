\section{Security and Trust Boundaries}
\label{sec:trust}

The platform has several layers, each with distinct authentication and trust assumptions. This section defines their guarantees, boundaries, and excluded threats.

\subsection{Transport: Hop-by-Hop Encryption and Authentication}

A connection between two neighboring peers is established by an authenticated ephemeral Diffie-Hellman key exchange, after which traffic is protected by authenticated symmetric encryption. The initial hello is encrypted to the recipient's long-term identity key, so a peer does not respond to a hello it cannot decrypt, and its port is invisible to a passive scanner.

This authentication is \emph{hop-by-hop}. A request that traverses peers $A \to B \to C \to D$ is authenticated by $A$ to $B$, by $B$ to $C$, and by $C$ to $D$. There is no transport-level guarantee that the message body at $D$ is the body $A$ originally sent: an intermediate peer can drop, reorder, or modify the payload before forwarding.

\subsection{Application Layer: End-to-End Authentication via Validity Predicates}

End-to-end integrity is the contract's responsibility. A contract's validity predicate $\valid_\contract$ runs at every peer that touches the state. Update messages typically include a signature by an application-authorized key over the update content; the validity predicate verifies the signature and rejects the update otherwise. Because $\valid_\contract$ is itself part of the contract's content-addressed code, a peer cannot serve a state that fails validity without being caught by every receiving peer that runs the same code.

The combination is the platform's substitute for a single end-to-end transport channel. Transport gives hop-by-hop confidentiality and authentication of neighbors. The contract gives end-to-end semantic integrity of state.

\subsection{Location Assignment: A Known Sybil and Grinding Surface}

A peer's location is a hash of its externally observed network address, taken over the address \emph{prefix}: the /24 of an IPv4 address, so all hosts in the same /24 share a location, and a site-level prefix of an IPv6 address. This raises the cost of location grinding, since an adversary who wants peers at chosen ring locations needs many distinct prefixes rather than many hosts in one subnet.

Prefix hashing only raises that cost. An adversary who can rent address space across many /24s, obtain an IPv6 range, or provision machines across distinct cloud prefixes can still concentrate peers in chosen ring regions, then selectively answer requests for contracts there or crowd honest peers out of the topology.

Prefix hashing also places every honest peer sharing a prefix at the \emph{same} location: independently operated peers behind a university or corporate NAT, a carrier-grade NAT pool, or a popular cloud region have ring distance zero from one another. This affects three things. \emph{Topology construction:} gap-targeting (\cref{sec:routing}) assumes neighbor locations spread around the ring, and a cluster of co-located peers is a zero-width spike to it; and an adversary able to grind locations on both sides of a target can occupy its predictable nearest-neighbor slots and attempt a local eclipse, although failed links are still removed. \emph{Replication:} peers near a contract's location are meant to protect against a single peer serving stale or doctored state, but co-located peers may share an operator and failure domain. \emph{Sybil defenses:} the application-layer defenses below depend on honest peers being diverse near critical locations, which shared prefixes make less likely. Adding a per-peer nonce would spread co-located peers but would restore the grinding freedom that prefix hashing removes.

The platform does not solve this at the location layer; two mitigations operate above it. First, validity predicates make forged state detectable: a state with an invalid signature is rejected by every honest receiver, so the remaining attack is to serve stale but valid state. Second, identity, reputation, and admission control are expected to be built as application-layer contracts (Ghost Keys \citep{ghostkey} is an example of a contract-mediated anonymous identity scheme). A contract that publishes authoritative information can require its writers to hold reputation tokens issued by another contract; an inbox contract can demand a small proof of work; a forum can require introductions from existing members. A platform-level scheme would either impose a particular economic or identity model or provide a generic obstacle that a well-resourced adversary could overcome.

These application-layer contracts are, however, routed and replicated through the same location layer. An attacker with enough prefixes to crowd a contract's location can serve stale reads of it and keep honest writes from reaching its replicas. Bootstrapping these defenses therefore needs a property the platform does not yet provide: diversity among the peers near safety-critical contracts, separation of their replicas on the ring, or an out-of-band trust anchor such as a bundled root key.

\subsection{Delegates: A Trust Boundary Around Secrets}

Applications also have private state (a user's signing keys, a private contact list, the decryption material for an encrypted inbox) that should never be replicated and should be accessible only through controlled interfaces. A delegate (\cref{sec:primitives}) holds such state inside the local Freenet Core, and user interfaces and other delegates reach it only by sending messages. For a message from a user interface, the sender identifier is the contract that delivered that interface; for a message from another delegate, it is that delegate's key, a hash of its code and parameters that different code cannot claim. A delegate's policy can therefore be ``respond only to the user interface delivered by contract X'' or ``respond only to delegate Y.''

Traditional in-process encapsulation (a ``private'' field on an object) is honored only by code that chooses to honor it, since the same address space gives access to memory, the file system, and undocumented interfaces. A delegate's secret state is not addressable from any other code on the device; the only way to obtain a secret is to convince the delegate, on the basis of sender identity and message contents, that releasing it is allowed. The boundary is enforced by the local Core, which is itself software on the same host, so a compromised Core can violate it. Defending against that would require hardware-attested execution, which the platform does not provide; the trust model assumes an uncompromised local Core.

\paragraph{Worked example: signing without exporting a key.} A chat application's UI needs to send signed messages. Without delegates, it must hold the private key. With delegates, the UI sends a $(\textsf{sign}, \mathrm{payload})$ message to a key-manager delegate; the delegate verifies the sender, signs the payload, and returns the signature. The private key never crosses the boundary. A bug or compromise in the UI can produce unwanted signed payloads but cannot exfiltrate the key itself; the delegate is also free to apply rate limits or user confirmation prompts before signing.

\paragraph{Acting on contracts.} A delegate can issue the same \textsf{GET}, \textsf{PUT}, and \textsf{SUBSCRIBE} requests as a user interface, and they are routed through the network in the same way; it can also submit \textsf{UPDATE}s to contracts its node already holds. When a contract it subscribes to changes, the local core notifies the delegate, and these subscriptions persist across restarts of the node. A delegate can therefore maintain an application's public state on the user's behalf, for example by publishing signed updates to a contract it subscribes to, without exposing the signing key to any user interface.

\paragraph{Background execution.} With the user's consent, a delegate may also run when no user interface is open: when the node starts and at periodic wake-ups, under a per-delegate budget of execution time and contract operations.

\paragraph{Cross-device replication.} A user typically runs the ``same'' delegate on several devices. The intended pattern for keeping those instances in sync is a shared-secret contract: a contract holding an encrypted, replicated copy of the shared private state, decryptable only by delegates that hold the key. The contract's merge function provides convergence and the delegate provides confidentiality. This pattern is not yet implemented (\cref{sec:status}), although the capabilities above supply what such a delegate needs: it can subscribe to the shared contract, be notified of changes made on another device, and merge them without a user interface being open.

\subsection{Resource Accounting and Its Limits}

Each peer rate-limits its transport bandwidth and the updates it accepts from each neighbor for each contract, and disconnects a neighbor that consumes excessive resources. Each WebAssembly invocation runs under a time limit and a memory limit enforced by Wasmtime \citep{wasmtime}, and the set of hosted contracts is bounded as described in \cref{sec:updates}.

These limits protect a peer against a single misbehaving neighbor, not against coordinated traffic from many neighbors or denial of service through many cheap identities. Addressing those attacks probably requires accounting that persists across identities (\cref{sec:status}).
